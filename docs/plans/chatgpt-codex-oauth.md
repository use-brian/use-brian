## Outcome

An OSS user can choose **Sign in with ChatGPT** during setup, complete the
browser flow with an eligible ChatGPT account, and run Brian on the OpenAI
models available to that account. No OpenAI API key is required for this path.

This is a subscription-auth provider, not another OpenAI-compatible API-key
endpoint:

- ChatGPT/Codex quota and plan limits remain OpenAI's authority.
- Brian discovers model availability from the authenticated Codex runtime.
- Gemini, Vertex, and DashScope remain supported side by side.
- Removing or losing the ChatGPT authorization removes the models from Brian's
  menus instead of leaving entries that fail when selected.

## Why this is a separate provider lane

Brian's existing `openai-compat` adapter speaks the Chat Completions protocol
to a configured endpoint with an API key. A ChatGPT subscription is different:
its OAuth credential, quota, model catalog, refresh lifecycle, and request
transport are owned by Codex. Treating the OAuth access token as
`OPENAI_API_KEY`, or sending it to a guessed backend URL, would create an
unsupported and fragile integration.

The first implementation therefore uses the public `codex app-server` protocol
as the boundary for sign-in, token refresh, model discovery, and inference.
Brian integrates with that protocol; it does not implement OpenAI's OAuth
client or persist OpenAI tokens itself.

The plan was checked against:

- OpenAI's current **Using Codex with your ChatGPT plan** guidance, which
  documents ChatGPT-plan sign-in for local Codex clients:
  <https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan>
- The JSON schemas generated by `codex app-server generate-json-schema
  --experimental` from Codex CLI `0.146.0-alpha.10.1` on 2026-07-27. The public
  seams used here are `account/login/start`, `account/read`, `model/list`,
  `thread/start`, `turn/start`, streamed item notifications, and
  `dynamicToolCall`.
- OpenClaw main at commit `c66ca2fbb2b038f4796abfa76bd52dcc3b675b02`
  (fetched 2026-07-27), especially its Codex app-server auth binding, model

`codex app-server` is still labelled experimental. Brian must pin the Codex
package version, test the generated protocol contract, and upgrade it
deliberately. No implementation may depend on fields marked "OpenAI internal
use only".

### Current implementation boundary

The implementation now reaches the OSS launcher, API, model menus, routing,
query loop, and localized Settings surface:

- `@openai/codex` is pinned to the schema-reviewed runtime version.
- A bounded, Zod-validated JSONL RPC peer owns initialization, correlation,
  notifications, server requests, cancellation, and shutdown.
- A managed process seam starts the pinned package over stdio with an isolated
  `CODEX_HOME`, an empty temporary working directory, and an allowlisted
  environment that excludes OpenAI/Codex API keys and access tokens.
- The managed P0 peer allowlists only `initialize` and `initialized`; generic
  callers cannot use it to start a thread or turn.
- The account surface expands that allowlist only for `account/read`,
  ChatGPT browser/device login start and cancel, logout, and `model/list`.
- Account results expose a masked email hint rather than raw credentials or
  tokens. Browser/device URLs must be HTTPS OpenAI or ChatGPT origins.
- Model discovery is paginated, bounded, duplicate-rejecting, and returns a
  reviewed normalized catalog; hidden models stay absent by default.
- The pinned-runtime request-capture test proves that the hardened inference
  profile exposes only Codex's isolated `exec`/`wait` code-mode envelope, and
  that the only callable operations inside that envelope are the
  Brian-supplied dynamic tools. Planning, skills, collaboration, shell, file,
  browser, computer, app, MCP, and hosted-search capabilities are absent.
- The `openai-codex` registry identities and provider factory exist. Routing
  accepts a live per-model entitlement catalog, so a cached provider cannot
  serve a model removed from `model/list`.
- The OSS API owns one restart-bounded manager, keeps the local control routes
  available even when the binary cannot start, and clears model entitlement on
  account/catalog/transport refresh failures.
- The routing boundary re-resolves boot-selected internal lanes against live
  availability on every call, so completing OAuth activates Codex-only
  background and extraction work without a process restart.
- Authenticated local routes expose masked status, browser/device login,
  cancellation, logout, and atomically persisted provider preference. No token
  shape is present in the route or browser types.
- The launcher permits a credential-free ChatGPT choice and hands the user to
  Settings → AI providers. The localized card opens the validated browser URL,
  supports device-code fallback, polls masked status, lists only reviewed live
  models, and can switch the preferred backend even while Codex is unavailable.

The account surface remains incapable of starting a model turn. Only the
hardened inference surface can do so, and provider routing exposes it only
after the authenticated catalog intersects a reviewed active registry row.

## Locked decisions

1. **Codex manages OAuth.** Brian starts `account/login/start` with
   `{type: "chatgpt"}`, opens the returned authorization URL, waits for
   `account/login/completed`, and verifies the result through `account/read`.
   Brian never receives, parses, logs, or stores the access or refresh token.
2. **Isolated credential home.** The managed Codex process runs with an
   OSS-owned home under `~/.usebrian/codex/`. It does not read or write the
   user's global `~/.codex` login. This avoids refresh-token rotation races and
   keeps disconnect/recovery scoped to Brian.
3. **Pinned runtime, not a global executable assumption.** The OSS distribution
   pins `@openai/codex` and resolves its bundled binary. A globally installed
   `codex` may be offered only as an explicit development override.
4. **Account discovery gates model visibility.** Brian calls `model/list` after
   login and on reconnect. Registry metadata may describe known models, but a
   model appears in a menu only when the authenticated catalog returns it.
   Brian never infers entitlement from a ChatGPT plan name.
5. **No silent model substitution.** If an explicitly selected OpenAI model is
   no longer available, the turn returns a reconnect/reselect error. Brian may
   choose the Codex catalog's default only when the user selected an `Auto`
   tier and the request explicitly allows provider fallback.
6. **Brian remains the agent harness.** Codex supplies the model transport;
   Brian still owns memory, context assembly, tool policy, confirmations, tool
   execution, analytics, compaction, and persistence.
7. **Native Codex actions fail closed.** The provider starts ephemeral threads
   with no environment access, an empty working directory, no configured MCP
   servers, and Brian tools registered only as dynamic tools. The managed
   process disables every native capability and instruction surface supported
   by the pinned runtime under `--strict-config`. A request-capture contract
   test verifies that the residual `exec`/`wait` envelope is an isolated V8
   dispatcher whose complete nested tool set is exactly the Brian dynamic
   tools. Observing a native action and aborting afterward is not a security
   boundary; any extra nested or direct tool fails the contract.
8. **Subscription and API billing stay distinct.** ChatGPT quota is not mapped
   onto Brian's per-token metered ledger. A future `OPENAI_API_KEY` provider is
   a separate OpenAI Platform lane with its own pricing and usage accounting.
9. **OSS first.** V1 is local single-player only. Hosted/team support is
   deferred because server-side storage of per-member subscription credentials,
   workspace routing, compliance, and support boundaries need a separate
   product decision.

## Architecture

### 1. Managed app-server client

Add `packages/core/src/providers/codex-app-server/`:

- `protocol.ts` — the reviewed, minimal Zod protocol fixture for the pinned
  runtime version; no generated-schema bundle is vendored.
- `process.ts` — starts the pinned Codex binary over stdio, with
  `CODEX_HOME=~/.usebrian/codex`, a minimal environment, an empty temporary
  working directory, bounded stderr, shutdown, restart, and abort handling.
- `rpc.ts` — JSON-RPC request/response correlation and notification fan-out;
  Zod validates every message crossing the process boundary.
- `auth.ts` — `account/read`, `account/login/start`,
  `account/login/cancel`, login-completion notifications, and logout. Its
  public result contains only masked account metadata (`type`, optional masked
  email hint, plan label, connected state).
- `catalog.ts` — paginated `model/list`, normalized model IDs, display names,
  input modalities, supported reasoning efforts, and default marker.
- `provider.ts` — implements Brian's `LLMProvider` and maps Codex events to
  Brian `StreamChunk`s.

The client is a process singleton per OSS API process. Provider sessions are
isolated logical threads over that client. A crash fails the active turn,
restarts once with backoff, and re-checks `account/read`; it never loops
indefinitely.

### 2. Model registry and routing

Extend `ModelProvider` with a dedicated `openai-codex` key. Do not reuse
`openai-compat:*`: the protocols and billing modes differ.

Known OpenAI rows carry curated Brian metadata (class, context budget,
capabilities), but availability is the intersection of:

1. active `openai-codex` registry rows; and
2. IDs returned by the live `model/list` catalog.

This requires changing provider availability from a bare `Set<providerId>` to
a catalog shaped like:

```ts
type ConfiguredProvider = {
  provider: LLMProvider
  availableModels?: ReadonlySet<string>
}
```

Static providers omit `availableModels` and keep today's behavior. Codex
supplies it, so menus, `ensureServableModel()`, and dispatch all enforce the
same account-specific catalog. Unknown models returned by Codex stay hidden
until Brian has a reviewed registry row; discovery is an entitlement gate, not
an uncontrolled registry extension.

OSS setup records a **preferred provider** (`gemini`, `openai-codex`,
`dashscope-intl`, or `auto`) in `~/.usebrian/config.json`. Tier aliases resolve
within that provider first, then apply the existing same-class fallback rule.
This lets an OAuth user choose ChatGPT without changing hosted plan tiers or
making OpenAI the default for existing installs.

The pinned runtime's reviewed 2026-07-27 public catalog establishes the initial
OSS auto-routing map: Luna → Standard, Terra → Pro, Sol → Max, and GPT-5.5 →
Research. GPT-5.2 remains a directly selectable Research alternative. These are
OSS routing/budget groups; hosted never configures `openai-codex`, and
ChatGPT-plan traffic never enters Brian's metered-credit ledger. Every row is
still intersected with the authenticated `model/list` result, so the registry
does not manufacture entitlement. Behavioral evaluation remains a release
hardening gate and may adjust these mappings before the README moves to
Supported.

### 3. Query-loop bridge

Codex app-server dynamic tools are request/response RPC, while Brian's query
loop consumes a streamed tool call, executes it under Brian policy, then calls
`ProviderSession.send()` again with the result. The adapter bridges those two
state machines:

1. `createSession()` starts an **ephemeral** Codex thread with Brian's Layer 1
   prompt as developer instructions, the selected model, the two-level
   reasoning mapping, `environments: []`, and Brian tool schemas as
   `dynamicTools`. Provider transport instructions remain tool-agnostic; the
   injected dynamic-tool descriptions are the only place tool-specific
   capability text appears.
2. The first `send()` starts a Codex turn. The latest user content is normal
   turn input; earlier bounded persisted history is appended with
   `thread/inject_items` as model-visible Responses items. The Codex thread is
   ephemeral, so Brian's DB remains the durable source of truth.
3. Agent-message deltas map to `text_delta`; supported reasoning-summary deltas
   map to `thinking_delta`; token-usage notifications map to `TokenUsage`.
4. On a `dynamicToolCall` server request, the adapter emits
   `tool_use_start` / `tool_use_delta` / `tool_use_end`, emits
   `message_end {stopReason: "tool_use"}`, and parks the JSON-RPC request.
5. Brian executes the tool with its existing allow/ask/block and confirmation
   paths. The next `send()` matches the resulting `tool_result` by call ID,
   answers the parked RPC with `DynamicToolCallResponse`, and resumes streaming
   the same Codex turn.
6. `turn/completed` maps the upstream terminal status. Cancellation interrupts
   the native turn, rejects all parked tool calls, and kills the process only
   when the RPC client cannot recover.

Parallel tool calls are supported as one parked batch. The adapter does not
answer any call until every tool result in the batch is present; a missing or
duplicate result fails closed with the offending call IDs.

Implemented contract coverage also includes response/first-event coalescing in
one JSONL read, fail-open structured-output retry only for JSON-RPC
`invalid params`, exact-model catalog rejection, and cleanup of ephemeral
threads.

The stateless `stream()` method uses the same machinery with one ephemeral
session. JSON output maps `responseSchema` to `turn/start.outputSchema` where
available; schema rejection falls back once to the existing hint-only behavior,
matching Brian's current liveness contract.

### 4. OSS setup and settings

The launcher changes from "prompt for one Gemini key" to a provider choice:

1. **Sign in with ChatGPT** — starts the API without requiring a model API key,
   opens the authenticated local app, and points the user to Settings → AI
   providers. The Settings card starts the browser authorization and polls the
   callback result.
2. **Gemini API key** — the persisted key path.
3. **Vertex AI or DashScope** — remain environment-configured paths and skip
   the interactive credential prompt when present.

Non-interactive/headless setup uses the app-server's
`{type: "chatgptDeviceCode"}` response and displays only the verification URL
and one-time user code. The launcher must not print tokens or raw account
objects.

Settings → AI providers gains a localized provider card with:

- connected/disconnected state;
- masked email when the user consents to display it;
- provider-reported plan label and quota status as informational data only;
- Connect, Reconnect, and Disconnect actions;
- the account-scoped model list and preferred-provider choice.

Every string lands in all locale dictionaries in the same commit.

### 5. Recovery and observability

- `401` or `reauthenticationRequired` marks the provider unavailable and
  surfaces **Reconnect ChatGPT**. No fallback reads from `~/.codex`.
- Rate-limit errors include provider reset metadata when available and never
  claim Brian credits were exhausted.
- Analytics records provider/model, latency, terminal status, and token counts.
  It never records auth URLs, login IDs, email, tokens, or raw RPC payloads.
- Disconnect invokes app-server logout and removes the isolated Brian Codex
  credential store through the app-server-owned flow. Files are not manually
  deleted while the process is running.
- A protocol-version mismatch disables only `openai-codex`, logs the expected
  and observed versions, and leaves other configured providers usable.

## Security invariants

- Never read `.env` or `~/.codex/auth.json` into logs, prompts, tests, or UI.
- Never accept pasted ChatGPT access or refresh tokens.
- Never expose the app-server listener beyond stdio/loopback.
- Deny native tools before execution. `sandbox: "read-only"` and
  `approvalPolicy` are defense in depth, not substitutes for a pre-tool deny
  boundary.
- Validate auth URLs as HTTPS OpenAI origins before opening a browser.
- Treat model names, account metadata, RPC errors, and streamed content as
  untrusted input.
- Bound every line/frame, pending RPC count, stderr buffer, and login/turn
  timeout.
- Preserve Brian's confirmation policy; OAuth does not grant a model permission
  to bypass tool governance.
- Do not advertise a model until both the registry row and live account catalog
  agree it is callable.

## Phasing

### P0 — Protocol fixture and process seam (implemented)

- Pin the Codex package.
- Check in a minimal, reviewed protocol fixture for only the methods Brian
  consumes; do not vendor the full generated schema bundle.
- Build the Zod-validated stdio client, lifecycle, and fake app-server test
  harness.
- Prove a pre-execution dynamic-tools-only boundary against the real pinned
  app-server. The test deliberately asks for shell, file, web, computer, and
  MCP actions and verifies no side effect occurs. Stop the project here if the
  pinned runtime cannot provide that guarantee.

### P1 — OAuth and catalog (implemented)

- Build auth and catalog operations on the existing isolated `CODEX_HOME`.
- Implement browser and device-code login, account status, logout, and model
  discovery.
- Add launcher and Settings provider surfaces only after the API lifecycle can
  hold the singleton process safely.
- Keep inference disabled until P2 passes.

### P2 — Provider and tool bridge (implemented)

- Implement ephemeral threads, message/reasoning/usage streaming, dynamic-tool
  parking/resume, aborts, and JSON schema output.
- Add `openai-codex` routing plus account-specific menu gating.
- Run the behavioral-evals matrix against every proposed tier mapping.

### P3 — OSS release hardening

- Package the pinned binary for supported macOS, Linux, and Windows targets.
- Exercise browser callback and device-code flows on clean machines.
- Add upgrade, revoked-token, quota exhaustion, app-server crash, and protocol
  mismatch recovery tests.
- Update the README table from **Planned** to **Supported** only after the full
  test and smoke gates pass.

## Test gates

Unit and contract tests must cover:

- partial/malformed/oversized JSON-RPC frames;
- auth URL allowlisting and redaction;
- login success, cancel, timeout, revoked refresh, and device-code mode;
- catalog pagination, hidden models, removed entitlement, and no silent
  downgrade;
- text, reasoning, usage, one tool call, parallel tool calls, tool error, and
  missing/duplicate tool results;
- refusal of native shell/file/computer/MCP actions;
- real-runtime proof that native actions are denied before any side effect;
- disconnect during login, inference, and a parked tool call;
- app-server crash/restart without duplicating a tool side effect;
- Gemini-only, Codex-only, and mixed-provider boots;
- absent OAuth means absent models in every menu.

Before release:

```bash
pnpm test
pnpm smoke
pnpm check
pnpm typecheck
```

One live, opt-in integration suite may run only when a disposable ChatGPT test
account is already authenticated in the isolated test home. CI must never
require or import a developer's personal Codex login.

## Done when

- A clean OSS install can choose ChatGPT, complete browser or device-code
  sign-in, discover only the account's available models, and finish a Brian
  chat turn with multiple governed tool calls.
- Restarting Brian preserves the isolated authorization without copying global
  Codex state.
- Revocation, quota exhaustion, and catalog changes produce actionable states
  without breaking Gemini, Vertex, or DashScope.
- No OpenAI token is present in Brian config, database rows, logs, analytics,
  browser responses, or test fixtures.
- The public README says **Supported**, not **Planned**, only after all gates
  above pass.
